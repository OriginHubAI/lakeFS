# lakeFS Enterprise 功能自研排期文档

> 创建时间：2026-03-03  
> 目标：评估在 lakeFS 开源版本上自研 Enterprise 功能的可行性与投入产出比

---

## 一、功能概览

| 功能 | Enterprise 描述 | 难度 | 工作量 | 优先级建议 |
|------|-----------------|:----:|:------:|:----------:|
| 异步 Commit/Merge | 非阻塞操作，适合大仓库 | ⭐⭐⭐ | 1-2 周 | P1 |
| Redis 数据库支持 | 高性能 KV 存储 | ⭐⭐⭐ | 2-3 周 | P2 |

## 二、详细分析

### 1. 异步 Commit 与 Merge

#### 功能价值
- 大仓库（百万文件）的 Commit/Merge 可能需要几分钟
- 同步操作会导致 API 超时或客户端阻塞
- 异步模式让 API 立即返回 Task ID，后台执行

#### 技术分析
| 项目 | 说明 |
|------|------|
| 现有基础 | ✅ 任务框架完善（`RunBackgroundTaskSteps`、状态管理） |
| API 接口 | ✅ 已定义（`CommitAsync`、`MergeIntoBranchAsync`） |
| 核心改动 | 实现 `ExtendedOperations` 接口，替换 `NoopExtendedOperations` |
| 代码量 | ~500 行 Go 代码 |

#### 风险与挑战
- Merge 冲突处理需要特殊设计
- 多实例部署时的任务状态一致性
- 同一分支的并发操作排队策略

#### 工作量明细
| 阶段 | 任务 | 时间 |
|------|------|------|
| 设计 | 接口设计、冲突处理方案 | 2 天 |
| 开发 | ExtendedOperations 实现 | 4 天 |
| 测试 | 单元测试 + 集成测试 | 3 天 |
| 联调 | 端到端测试、边界情况 | 2 天 |
| **合计** | | **1.5-2 周** |

#### 结论
> ✅ **强烈推荐实现**  
> 投入小、收益大、风险可控。适合大数据量场景。

---

### 2. Redis 数据库支持

#### 功能价值
- PostgreSQL 在高并发场景下可能成为瓶颈
- Redis 作为元数据存储可提供更低延迟
- 支持 Redis Cluster 实现水平扩展

#### 技术分析
| 项目 | 说明 |
|------|------|
| 现有基础 | ✅ KV 抽象层设计良好（5 个接口方法） |
| 参考实现 | ✅ Postgres、DynamoDB、CosmosDB 实现可参考 |
| 配置结构 | ✅ Redis 配置已定义（`pkg/config/config.go`） |
| 核心改动 | 新增 `pkg/kv/redis/store.go` |
| 代码量 | ~500 行 Go 代码 |

#### 风险与挑战
- **Scan 有序性**：lakeFS 要求按 key 有序扫描，Redis `SCAN` 不保证顺序
  - 方案 A：使用 Sorted Set（推荐）
  - 方案 B：扫描后内存排序（数据量大时有问题）
- **SetIf (CAS)**：需要 Lua 脚本实现原子性
- **Redis Cluster**：key 需在同一 slot，要设计 hash tag

#### 工作量明细
| 阶段 | 任务 | 时间 |
|------|------|------|
| 设计 | Key 编码方案、Scan 有序性方案 | 2 天 |
| 开发 | Driver + Store 实现 | 5 天 |
| 开发 | Cluster 模式支持 | 3 天 |
| 测试 | 单元测试 + 压力测试 | 3 天 |
| 联调 | 与 lakeFS 集成测试 | 2 天 |
| **合计** | | **2-3 周** |

#### 结论
> ⚠️ **视需求决定**  
> PostgreSQL 对大多数场景够用。除非有明确的性能瓶颈，否则优先级不高。

### 3. RBAC 权限控制

#### 功能价值
- 团队协作需要权限隔离（谁能访问哪个仓库/分支）
- 合规要求（审计、最小权限原则）
- 多租户场景的必备功能

#### 技术分析
| 项目 | 说明 |
|------|------|
| 现有基础 | ✅ 权限评估引擎完整（ARN 匹配、Deny 优先、条件支持） |
| API 接口 | ✅ Policy CRUD 接口已定义（被 501 禁用） |
| 参考实现 | ✅ `contrib/auth/acl` 有完整 Auth 服务 |
| 核心改动 | 合并 ACL 服务到主程序 + 解除 API 限制 + UI |
| 代码量 | ~2000 行 Go + ~1500 行 React |

#### 实现方案对比
| 方案 | 说明 | 工作量 | 推荐度 |
|------|------|--------|--------|
| A. 部署 ACL 服务 | 使用现有 `contrib/auth/acl` | 1-2 天 | ⭐⭐⭐⭐ |
| B. 内置 RBAC 服务 | 合并到 lakeFS 主程序 | 5-7 周 | ⭐⭐⭐ |

#### 方案 A（快速方案）工作量
| 阶段 | 任务 | 时间 |
|------|------|------|
| 部署 | 构建 ACL 服务镜像 | 0.5 天 |
| 配置 | docker-compose 集成 | 0.5 天 |
| 测试 | 功能验证 | 1 天 |
| **合计** | | **2 天** |

#### 方案 B（完整方案）工作量
| 阶段 | 任务 | 时间 |
|------|------|------|
| 设计 | 架构设计、迁移方案 | 3 天 |
| 开发 | 合并 ACL 服务逻辑 | 1 周 |
| 开发 | 解除 Policy API 限制 | 1 天 |
| 开发 | Web UI 策略管理 | 1.5 周 |
| 测试 | 权限场景全覆盖测试 | 1 周 |
| 文档 | 配置文档、迁移指南 | 2 天 |
| **合计** | | **5-7 周** |

#### 风险与挑战
- ACL 与完整 RBAC 不能共存，需明确取舍
- Web UI 工作量较大（React 前端）
- 从 `simplified` 模式迁移需要数据兼容

#### 结论
> ✅ **推荐方案 A 快速上手**  
> 组级 ACL 权限（Read/Write/Super/Admin）满足大部分场景。  
> 如果需要细粒度策略控制，再投入方案 B。

### 4. Standalone GC（垃圾回收）

#### 功能价值
- 定期清理已删除/过期的对象，释放存储空间
- Spark GC 需要搭建 Spark 环境，运维成本高
- Standalone GC 以 Docker 镜像运行，开箱即用

#### 技术分析
| 项目 | 说明 |
|------|------|
| 现有基础 | ⚠️ Spark GC 在 `clients/spark`，Scala 实现 |
| 核心逻辑 | 列出对象存储 → 获取活跃引用 → 差集 = 可删除 |
| 难点 | SSTable 解析、大数据量流式处理、多存储支持 |
| 代码量 | ~3000 行 Go 代码 |

#### 风险与挑战
- **SSTable 解析**：需要移植 Scala 代码到 Go
- **内存管理**：百万级对象不能全加载到内存
- **存储适配**：只支持 S3，Azure/GCS 需额外工作
- **并发安全**：GC 运行时的写入需要处理

#### 工作量明细
| 阶段 | 任务 | 时间 |
|------|------|------|
| 设计 | 架构设计、流式处理方案 | 1 周 |
| 开发 | 对象存储列表扫描 | 1 周 |
| 开发 | SSTable/Parquet 解析 | 1.5 周 |
| 开发 | 差集计算与报告生成 | 1 周 |
| 开发 | 多存储支持（可选） | 1 周 |
| 测试 | 大数据量测试 | 1 周 |
| **合计** | | **6-8 周** |

#### 替代方案
| 方案 | 说明 | 推荐度 |
|------|------|--------|
| Spark GC | 使用 local Spark 或托管 Spark | ⭐⭐⭐⭐ |
| 增大 retention | 设置更长的保留期，减少 GC 频率 | ⭐⭐⭐ |
| 手动清理 | 脚本定期清理明确过期的数据 | ⭐⭐ |

#### 结论
> ❌ **不推荐自研**  
> 复杂度高、坑多、投入产出比低。建议使用 Spark GC 或增大 retention 策略。

## 四、投入产出分析

### 成本 vs 收益矩阵

```
                    高收益
                      │
     异步 Commit ★    │
                      │
    ──────────────────┼──────────────────
                      │
          ACL 服务 ★  │   Redis ◆
                      │
    ──────────────────┼──────────────────
                      │      Standalone GC ✗
                      │      内置 RBAC ◆
                      │
低成本 ───────────────┼─────────────────── 高成本
                      │
                    低收益

★ = 强烈推荐   ◆ = 视需求   ✗ = 不推荐
```

### 决策建议

| 场景 | 推荐实现 |
|------|----------|
| 大数据量仓库（百万文件） | 异步 Commit/Merge |
| 团队协作需要权限隔离 | 部署 ACL 服务 |
| 有明确的 PostgreSQL 性能瓶颈 | Redis 支持 |
| 需要完整的策略管理 UI | 内置 RBAC |
| 需要自动垃圾回收 | 使用 Spark GC |

## 五、总结

### 值得做的功能

| 功能 | 理由 |
|------|------|
| **异步 Commit/Merge** | 投入小（1-2周）、基础设施完善、对大仓库收益明显 |
| **部署 ACL 服务** | 几乎零开发成本、快速获得权限控制能力 |

### 视需求决定的功能

| 功能 | 理由 |
|------|------|
| **Redis 支持** | PostgreSQL 通常够用，除非有明确性能瓶颈 |
| **内置 RBAC** | 投入较大（5-7周），ACL 服务已满足大部分需求 |

### 不建议做的功能

| 功能 | 理由 |
|------|------|
| **Standalone GC** | 复杂度高、坑多、Spark GC 是更好的选择 |
